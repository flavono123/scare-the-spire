# 카드 아트를 깨우되, 새 픽셀은 아껴라

결론부터 말하면, 모드는 **지금 별도의 멀티모드 모노레포로 분리**하고, 첫 모드 '정식 카드 아트의 강화 버전'은 **기술적으로 구현 가능하다**. STS2 v0.111.0은 Godot 4.5.1 Mono 위에 공식 모드 로더와 Harmony 2.4.2를 동봉하고 있어서, UI 계층 메서드에 postfix만 걸고 카드 노드에 애니메이션 씬을 덧붙이는 순수 데코레이터가 성립한다. 위험은 등급을 따라 올라간다. 일반 등급의 프레임 안 연출은 위험이 낮고, 손패 위 팝아웃은 중간이다. 무대·크리처 연출은 크리처 애니메이션 트리거·히트스톱·화면 흔들림을 금지하고 '덧그리기'로 한정해야 데코레이터로 남는다. 아트 생산에서 Cloudflare Workers AI는 하루 약 80장의 FLUX.2 [klein] 4B 편집을 무료로 주는 **보조 차선**일 뿐이며, 영상·깊이·분할 모델은 없다. '바닐라라고 믿을 만한' 품질은 원본 픽셀을 마스크·컷아웃으로 재사용하고 엔진 안에서 셰이더로 움직이는 공정, 즉 생성 픽셀을 최소화하는 공정에서 나온다. 검증의 정본은 게임과 같은 Godot 4.5.1 로컬 샌드박스이고, 사이트의 카드 타일 조합기는 dev 전용 근사 미리보기로 역할을 낮춰야 한다. "등급이 오를수록 프레임을 넘는 카드"라는 개념은 Marvel Snap·Hearthstone과 STS2 모드 IroncladFX가 이미 보여 줬다. 그러나 공식 아트 보존, 희귀도 단계, 전 카드 규칙, 비지속, 바닐라 화풍을 동시에 갖춘 모드는 STS1·STS2 어디에도 없다. 가장 큰 위험은 '바닐라와 구별 불가'라는 목표에 AI가 더해지는 조합이 Mega Crit의 반AI 입장과 정면으로 겹친다는 점이다. 그래서 출하 픽셀의 AI 비중을 0에 가깝게 설계하는 것이 품질과 평판을 함께 지키는 해법이 된다. 근거는 로컬 설치본 v0.111.0(2026-08-13 빌드) 디컴파일과 2026-10-18 기준 웹 조사다.

## (1) 레포는 지금 분리하라: 빌드·배포·평판 세 축이 모두 갈린다

**판정: 별도 레포로 분기한다. 비용은 코드가 한 줄도 없는 지금이 가장 싸다.** 두 프로젝트가 공유하는 것은 게임 데이터 몇 가지뿐이다. 사이트는 Next.js 15·pnpm 프로젝트이고, `main`에 push하면 GHA가 Cloudflare Workers로 배포한다([CLAUDE.md](../CLAUDE.md)). 모드는 `Godot.NET.Sdk/4.5.1`·`net9.0` C# 프로젝트다. 로컬 게임 설치본의 `sts2.dll`과 `0Harmony.dll`을 참조해 빌드하고, PCK는 MegaDot(Mega Crit의 Godot 포크) 또는 Godot 4.5.1로 export해야 한다. 커뮤니티 표준 템플릿은 **"Godot 버전이 더 새로우면 게임이 .pck를 로드하지 않는다"**고 경고한다([ModTemplate-StS2](https://github.com/Alchyr/ModTemplate-StS2)). 빌드에 독점 게임 DLL이 필요하므로 GitHub 호스티드 러너로는 합법적으로 빌드할 수 없다. 대표 라이브러리 BaseLib조차 워크플로 없이 로컬 빌드와 수동 릴리스로 운영된다([BaseLib-StS2](https://github.com/Alchyr/BaseLib-StS2)). 한 레포에 섞으면 모드 커밋마다 사이트 배포가 돌지만, 사이트 CI는 정작 모드를 빌드하지 못한다.

"여러 모드를 만들 수 있다"는 고려는 분리를 더 강하게 지지한다. STS2에서는 모드마다 레포를 두는 것이 일반적이다. 하지만 `luojiesi/SLS2Mods`처럼 여러 모드를 폴더별 csproj·매니페스트, 공용 툴, Workshop 업로드 작업 공간으로 묶은 모노레포도 이미 검증된 형태다([SLS2Mods](https://github.com/luojiesi/SLS2Mods)). 로더는 모드마다 고유 `id`를 요구하고, 매니페스트 옆에 `<id>.dll`·`<id>.pck` 이름의 파일을 둬야 한다([생태계 노트: ModManager 디컴파일](<../research_notes/슬더스2 카드 아트 모드 타당성/sts2_modding_ecosystem.md>)). 그래서 공용 코드는 각 DLL에 소스로 컴파일하거나 별도의 의존 모드로 내야 한다. v0.108.0부터는 한 모드가 여러 어셈블리를 등록할 수 있다([v0.108.0 패치노트](../data/sts2-patch-notes/v0.108.0.md)). Mega Crit 공식 업로더도 모드마다 `workshop.json`, `content/`, 1 MB 미만 `image.png`로 된 작업 공간을 전제한다([megacrit/sts2-mod-uploader](https://github.com/megacrit/sts2-mod-uploader)). 이 구조는 뒤 위험 절의 완화책에도 직접 쓰인다. **AI 보조 아트가 들어간 콘텐츠를 핵심 모드와 다른 모드로 떼어 낼 수 있기 때문이다.**

이 레포에는 이미 같은 위상의 선례가 있다. 쇼츠는 별도 로컬 레포 `slseoun-shorts`에서 만들고, 이 사이트는 `pnpm shorts:capture` 같은 명령으로 렌더만 공급한다([shorts-asset-handoff 스킬](../.claude/skills/shorts-asset-handoff/SKILL.md)). 모드도 같은 관계로 두면 된다. 사이트는 게임 데이터와 렌더의 SSOT이고, 위성 레포는 그 소비자다. 평판 격리도 이유다. 사이트의 일급 가치는 게임 번역을 따르는 정확한 백과사전이다. 모드의 AI 보조 아트 논란이 사이트 정체성으로 번지지 않게 막는 편이 낫다. 아트 원본의 무게도 다르다. 사이트의 카드 초상화만 633장·49 MB다([저작·미리보기 노트](<../research_notes/슬더스2 카드 아트 모드 타당성/animation_authoring_and_preview.md>)). 마스크, 컷아웃, PSD·Krita 원본은 이보다 커서 Git LFS나 레포 밖 보관이 필요하다.

단일 레포를 지지하는 논거도 가볍지 않다. 검증기에 재사용할 `src/components/codex/card-tile.tsx`, `@esotericsoftware/spine-player` 4.2.115, Canvas 2D VFX 근사기 `public/event-vfx-player.js`, PCK 리더 `scripts/lib/pck.py`가 모두 사이트에 있다. 하지만 이 결합은 단방향이고 얇다. 모드 레포가 카드별 매니페스트 JSON과 (선택적으로) 샌드박스 웹 빌드를 내보내고, 사이트의 dev 전용 라우트가 로컬 경로 환경 변수로 그것을 읽으면 충분하다. 레포 이름은 기존 관례를 따라 `slseoun-mods` 같은 형태를 권한다.

## (2) 구현은 가능하다, 크리처 '상호작용'은 덧그리기까지만

**판정: 조건부로 가능하다. 등급이 오를수록 위험도 오르고, 최상위 연출은 '덧그리기'로 정의를 좁혀야 데코레이터로 남는다.** 엔진 조건은 유리하다. STS2 v0.111.0은 .NET 9 위에서 도는 Godot 4.5.1 Mono 커스텀 빌드이고, **Harmony 2.4.2를 직접 동봉**한다. `sts2.dll`은 ReadyToRun 사전 컴파일이 없는 순수 IL이라 Harmony 패치가 잘 먹는다([sts2.dll v0.111.0 디컴파일](<../research_notes/슬더스2 카드 아트 모드 타당성/sts2_card_rendering_internals.md>)). 공식 로더 `ModManager`는 실행 파일 옆 `mods/`와 Workshop에서 매니페스트를 찾는다. 그다음 `{id}.dll`을 게임과 같은 AssemblyLoadContext에 올리고, `{id}.pck`를 `LoadResourcePack`(replaceFiles=true)으로 마운트한 뒤, `PatchAll`이나 `[ModInitializer]`를 실행한다(같은 출처). Mega Crit은 v0.107.1(2026-06-19)에서 "처음부터 통합 모드 로더가 있었다"고 밝히며 Workshop을 공식화했다([wiki.gg v0.107.1](https://slaythespire.wiki.gg/wiki/Slay_the_Spire_2:V0.107.1_-_Major_Update_2)). BepInEx 같은 외부 로더는 필요 없다.

### 카드 노드 구조가 연출의 자리를 정해 준다

모든 카드 UI는 풀링되는 `NCard`(`card.tscn`, 30장 프리웜) 하나로 그려진다. **초상화는 아틀라스 `AtlasTexture`를 쓰는 250×190 `TextureRect`이고, 어느 노드에도 클립이 없다.** 위에 덮인 `PortraitBorder`·`Frame` 텍스처가 가장자리를 숨길 뿐이다. 마스크 셰이더는 고대의 존재 카드에만 쓰는데, 이 셰이더는 내용물 크기를 598×842로 하드코딩하고 있다. 게임은 카드 내부 VFX 슬롯 `CardVfxContainer`와 카드별 오버레이 슬롯 `OverlayContainer`를 이미 갖고 있다([sts2.dll 디컴파일](<../research_notes/슬더스2 카드 아트 모드 타당성/sts2_card_rendering_internals.md>)). 바닐라에는 애니메이션 초상화도, 카드 씬 안의 SpineSprite도, 베타 아트 토글도 없다. 카드에 붙는 기존 움직임은 감염 카드의 약 30프레임 오버레이(AnimationPlayer와 공포증 모드 토글러), 고난(affliction) 셰이더 오버레이, 고대의 존재 배너 불꽃, 보상 화면의 희귀도 글로우·반짝이 정도다(같은 출처). 초상화 리소스를 모드 PCK로 덮어쓰는 방식은 효과가 없을 가능성이 높다. 커스텀 `AtlasResourceLoader`가 `.sprites/` 경로를 앞단에서 가로채 `.tpsheet`로 텍스처를 직접 만들기 때문이다. 그래서 **카드 노드에 자식 씬을 덧붙이는 방식**이 정답이다. 이 방식은 게임 텍스처를 런타임에 참조할 뿐이라 공식 아트를 재배포하지 않는다는 이점도 있다.

hover부터 사용까지 모든 단계에 UI 계층의 메서드나 시그널이 있다. 그래서 게임 상태 경로를 건드리지 않고 결과값을 바꾸지 않는 postfix만으로 트리거를 모두 얻을 수 있다(같은 출처).

| 이벤트 | 훅 (모두 UI 계층, postfix) | 쓰임새 |
|---|---|---|
| 부착·갱신 | `NCard.Reload()` | 카드 id로 모드 씬을 찾아 붙인다. 모든 화면 공통 |
| 정리 | `NCard.OnFreedToPool()` / `OnReturnedFromPool()` | 풀 반환 때 제거. 반환 시 시그널이 모두 끊기므로 매번 다시 연결한다 |
| hover | `NCardHolder.RefreshFocusState()`, `NPreviewCardHolder.OnFocus/OnUnfocus` | 손패·그리드·보상 공통 |
| 집기·취소 | `NHandCardHolder.BeginDrag()` / `CancelDrag()` | 팝아웃 시작·복귀 |
| 대상 hover | `NTargetManager.CreatureHovered/Unhovered` 시그널 | 타게팅 중 예고 연출 |
| 사용 확정(로컬) | `CardModel.TryManualPlay` (`__result == true`) | 게임 자체 `OnEnqueuePlayVfx`와 같은 시점 |
| 플레이 영역 도착(원격·자동 포함) | `NCombatUi.AddToPlayContainer(NCard)` | 원격 플레이어와 자동 사용 보완 |
| 인스펙트 | `NInspectCardScreen.Open` / `SetCard` | 상세 보기 감상 |

피해야 할 지점도 분명하다. `CardModel.OnPlayWrapper`·`OnPlay`, `Hook.*`, `CardPileCmd.*`는 게임 흐름이 await하는 async 경로라서, postfix가 첫 await 시점에 실행되고 예외가 나면 진행이 깨진다. `HoveredModelTracker`는 hover·선택 상태를 멀티플레이 피어에 동기화하므로 호출하면 안 된다. 가장 중요한 금지 항목은 `CreatureCmd.TriggerAnim`, `NHitStop`, 화면 흔들림이다. 이 셋은 **사운드를 내고, 크리처 Spine 상태를 바꾸며, `Engine.SetTimeScale`로 엔진 전체 시간을 늦춘다**(같은 출처). 크리처가 움찔하는 '진짜 반응'은 바닐라 연출의 타이밍을 바꾸므로 데코레이터 원칙과 충돌한다. 그래서 기획의 "크리처와 상호작용"은 **크리처 위에 덧그리는 연출**로 정의를 좁혀야 한다.

### 희귀도 사다리: 일반은 액자 안, 위로 갈수록 바깥으로

STS2 카드 598장의 희귀도 분포는 고급 232, 희귀 160, 일반 101, 고대의 존재 19, 기본 19이고, 나머지는 이벤트·저주·상태이상·토큰·퀘스트 67장이다. 캐릭터마다 기본 3~4, 일반 20~21, 고급 38~39, 희귀 27, 고대의 존재 2장이다([로컬 데이터 cards.json](../data/sts2/kor/cards.json)). 아래 사다리는 기획 원칙을 이 분포와 엔진 구조에 맞춘 권고안이다.

| 등급 (장수) | 연출 공간 | 트리거 | 기법 | 새 픽셀·AI |
|---|---|---|---|---|
| 기본·일반 (19+101) | 아트 프레임 안 (`%Portrait` 자식으로 `ClipContents` 250×190 Control) | hover·집기 때 재생, 사용 때 한 번 | 마스크 기반 셰이더(UV 흐름, 왜곡, 발광)로 원본 텍스처를 변조 | 없음 |
| 고급 (232) | 프레임 테두리를 살짝 넘는 스필 (`CardVfxContainer`) | 집기·사용 | 마스크로 원본 픽셀을 잘라 낸 전경 컷아웃을 프레임 위로 들어 올림 | 없음 (컷아웃이 원본보다 살짝 커지는 '들어 올림'이면 구멍이 드러나지 않는다) |
| 희귀 (160) | 손패 위 공간, 사용 때 대상 크리처까지 | 집기 때 팝아웃, 사용 때 투사체와 덧그린 타격 | 컷아웃, 게임 VFX 텍스처 재사용, 소형 스프라이트, 공용 파티클 | 좁은 띠 인페인팅, 소형 스프라이트 (사람 덧칠 포함) |
| 고대의 존재 (19) | 무대 전체 | 사용 | 카드별 수작업 연출. 틀 밖 요소는 마스크 셰이더가 걸린 CanvasGroup 바깥에 둔다 | 소수 수작업 |
| 이벤트·저주·상태이상 등 (67) | 일반 규칙 적용 또는 제외 | – | 고난·감염 오버레이가 있으면 그쪽을 우선 | 없음 |

이 배치는 상용 선례의 비용 구조와도 맞는다. Marvel Snap은 정적 프레임 브레이크를 Uncommon(초록)에, 아트 애니메이션을 그보다 위인 Epic에 둔다. **프레임 밖으로 나온 정지 컴포지트가 움직임보다 싸다**는 뜻이다([Marvel Snap Zone](https://marvelsnapzone.com/marvel-snap-progression-guide/)). 고급 등급을 '원본 픽셀 컷아웃의 스필'로 정의하면 232장이라는 최대 물량에 새 픽셀이 들지 않는다. 손패 팝아웃은 카드 transform을 따라야 하는 요소라면 `CardVfxContainer`에, 화면 공간에 고정해야 하는 요소라면 `NCombatRoom.Instance.Ui` 자식에 둔다. hover된 홀더는 `ZIndex=1`로 이웃 카드 위에 그려진다. 무대 연출은 게임과 같은 패턴을 따른다. `CombatVfxContainer`(크리처 앞)나 `BackCombatVfxContainer`(크리처 뒤)에 씬을 붙이고, 좌표는 `NCreature.VfxSpawnPosition`과 `Hitbox`로 잡는다([sts2.dll 디컴파일](<../research_notes/슬더스2 카드 아트 모드 타당성/sts2_card_rendering_internals.md>)).

### 데코레이터 계약: '없어도 되는 것'을 코드로 강제한다

기획의 원칙인 "코드 레벨에서 깨지지 않고 게임플레이에서 완전히 없어도 되는 것"은 다음 규칙들로 구현된다. 매니페스트에 **`"affects_gameplay": false`를 반드시 명시**한다. 기본값이 true라서, 빠뜨리면 상대에게 같은 모드가 없을 때 협동 접속이 `ModMismatch`로 거부된다([생태계 노트: HandshakeManager 디컴파일](<../research_notes/슬더스2 카드 아트 모드 타당성/sts2_modding_ecosystem.md>)). ModelDb에 들어가는 모델 타입과 넷 메시지를 정의하지 않는다. 모든 모드 Control은 `MouseFilter = Ignore`로 두어 카드 클릭·드래그 입력을 가로채지 않게 하고, 이웃 홀더의 위치는 읽기만 한다. 히트박스가 움직이면 오조작이 생기기 때문이다. postfix는 전부 try/catch로 감싼다. `TryManualPlay` postfix의 예외가 전파되면 실제 카드 사용이 실패할 수 있다. 난수는 `System.Random`이나 시각으로 시드되는 `Rng.Chaotic`만 쓰고 런 RNG는 절대 쓰지 않는다. 패치 대상이 `AccessTools.Method == null`이면 해당 기능만 조용히 끈다(같은 출처들).

비지속 원칙은 엔진 구조와도 잘 맞는다. 카드 자식으로 붙인 장식은 소멸 연출이 카드를 reparent해 침식 셰이더로 녹일 때 함께 녹는다. 다른 컨테이너에 띄운 틀 밖 요소는 애니메이션 길이 안에서 모드가 직접 정리한다. 바닐라 v0.110.0이 추가한 캐릭터별 형상 VFX, 즉 악마의 형상·메아리의 형상·사신의 형상·구렁이의 형상·공허의 형상처럼 캐릭터에 계속 붙는 연출([v0.110.0 패치노트](../data/sts2-patch-notes/v0.110.0.md))은 정확히 이 모드가 하지 않는 범주다. 게임에 '모션 감소' 설정은 없으므로, 존중할 기존 설정은 다음과 같이 매핑한다. `FastMode`가 Instant면 틀 밖 연출을 생략하고, Fast면 재생 시간을 줄인다. `PhobiaMode`가 켜지면 생물·벌레·피 계열 연출을 정지하고, `ScreenShakeOptionIndex`가 0이면 흔들림 연출을 금지한다. 여기에 모드 자체의 단계별 끄기 설정을 둔다([sts2.dll 디컴파일](<../research_notes/슬더스2 카드 아트 모드 타당성/sts2_card_rendering_internals.md>)).

### 사용 순간의 시간 창은 짧고, 신호 혼동은 치명적이다

게임은 사용한 카드를 플레이 영역으로 옮기는 Tween을 기본 0.25초, Fast 0.1초, Instant 0.01초로 돌리고, `OnPlayWrapper`가 이를 await하며 진행한다(같은 출처). 모드는 대기를 추가할 수 없으므로 사용 연출은 바닐라 흐름과 **병렬로, 짧게** 끝나야 한다. STS1에서도 "빠르고 경쾌한 반응"에 익숙한 플레이어에게 애니메이션 추가는 논쟁적이라는 지적이 있었고, 다중 시전 애니메이션을 빠르게 하는 모드(Fast Multi-Cast)가 따로 나올 만큼 템포 수요가 있었다([STS1 Steam 토론](https://steamcommunity.com/app/646570/discussions/0/1743357605565257724); [Workshop 검색](https://steamcommunity.com/workshop/browse/?appid=646570&searchtext=animated)). Hearthstone 골드 카드 팀의 원칙도 같은 방향이다. 애니메이션은 카드를 꾸며야지 초점이 되면 안 되고, 게임플레이 신호와 헷갈리면 안 된다. 연기 효과가 은신으로, 과한 붉은색이 격노로 오인될 수 있다는 사례가 있다([Hearthside Chat: Jon Briggs, 2015](https://hearthstone.blizzard.com/en-us/blog/18053404/)). STS2에 대입하면, 공격 카드의 덧그린 베기가 **추가 타격 횟수로 읽히면 안 된다.** 사용 가능 카드의 테두리 글로우, 고난 오버레이, 독의 초록색과 닮은 효과도 피해야 한다.

### 남는 기술 위험

가장 큰 공통 위험은 Early Access 패치마다 private 메서드명과 씬 구조가 바뀔 수 있다는 점이다. 카드가 많은 화면도 위험하다. 덱 보기나 도감 그리드에서 모든 카드를 상시 재생하면, 카드마다 있는 `PortraitCanvasGroup`의 재렌더 비용이 쌓인다. 실제 프레임 비용은 측정하지 못했으므로, hover된 카드와 사용 중인 카드만 재생하도록 제한해야 한다. 이 규칙은 "보드와 손패 전체가 프리미엄이어도 모든 플랫폼에서 원활해야 한다"는 Hearthstone의 최악 시나리오 예산보다 훨씬 가볍다([Jon Briggs, 2015](https://hearthstone.blizzard.com/en-us/blog/18053404/)). 게임은 원격 플레이어의 카드도 로컬에서 `NCard`로 그리므로 장식이 그 카드에도 붙는다. 이는 시각 차이일 뿐 동기화 문제는 아니다. 모드 씬은 전투방 프리로드 목록에 없으니, 첫 사용 때 생길 동기 로드 끊김을 전투 시작 시 미리 데워 막는 편이 좋다([sts2.dll 디컴파일](<../research_notes/슬더스2 카드 아트 모드 타당성/sts2_card_rendering_internals.md>)).

렌더러 선택도 판정에 들어간다. 게임에 spine-godot GDExtension(Spine 4.2)이 있어 Spine은 형식상 매력적이다. 하지만 카드 초상화 애니메이션의 핵심인 메시 변형은 **Professional 라이선스(세일가 $379, 정가 $449) 전용**이고 무료 에디션이 없으며, 체험판은 저장할 수 없다([Spine purchase](https://esotericsoftware.com/spine-purchase)). 무료이면서 네이티브 플러그인 없이 모드로 로드되는 저작 경로는 Godot 내장 2D 애니메이션뿐이다. Polygon2D와 Skeleton2D 메시 변형, AnimationPlayer, canvas_item 셰이더, GPUParticles2D가 여기에 해당한다([Godot 2D skeletons](https://docs.godotengine.org/en/stable/tutorials/animation/2d_skeletons.html)). "GIF처럼 보이는" 플립북은 피해야 한다. 1000×760 RGBA 프레임은 VRAM 기준 장당 약 2.9 MiB이고, 600장 규모라면 다운로드가 0.6~1.2 GB로 불어난다는 추정이 나온다([저작·미리보기 노트](<../research_notes/슬더스2 카드 아트 모드 타당성/animation_authoring_and_preview.md>)). 영상 방식의 Celestial Card Art는 애니메이션 아트 20점에 파일이 332 MB였다([Steam Workshop](https://steamcommunity.com/sharedfiles/filedetails/?id=3803362518)). GIF 교체 도구 Card Art Editor에는 "240초에 한 프레임"이라는 성능 불만 댓글이 달렸다([Steam Workshop](https://steamcommunity.com/sharedfiles/filedetails/?id=3748210488)).

## (3) Workers AI는 하루 약 80장짜리 보조 차선이다, 품질은 원본 픽셀에서 나온다

**판정: Workers AI를 쓰되, 역할을 '좁은 채움과 소형 스프라이트 시안'으로 한정한다. 움직이는 아트 자체는 AI로 생성하지 않는다.** Workers AI의 무료 할당은 하루 10,000 Neurons(00:00 UTC 초기화)다. 2026-10 기준 이미지 모델 10종 가운데 무료 할당으로 쓸 만한 참조 이미지 편집 모델은 **FLUX.2 [klein] 4B 하나**다. 출력 512² 타일당 26.05, 입력 타일당 5.37 Neurons이므로, 1 MP 이미지 편집(참조 1장)은 하루 약 79장, 텍스트만으로 생성하면 약 95장이 나온다. FLUX.2 [dev]는 하루 약 2장, klein 9B는 6~7장, Leonardo 계열은 3~4장이라 무료 할당으로는 사실상 못 쓴다([Workers AI pricing](https://developers.cloudflare.com/workers-ai/platform/pricing/); [Workers AI models](https://developers.cloudflare.com/workers-ai/models/?tasks=Text-to-Image); 장수는 단가로부터 계산한 값). 결정적인 공백도 있다. Workers AI 이미지 카탈로그에는 **영상·깊이·분할 모델이 없다.** 마스크를 받는 인페인팅 모델도 2022년 세대의 SD 1.5 인페인팅(베타, 단가 $0)뿐이다. FLUX.2 계열 모델 페이지에는 마스크 파라미터가 문서화돼 있지 않으므로, 원본을 그대로 지키려면 결과를 자체 마스크로 다시 합성해야 한다([SD 1.5 inpainting](https://developers.cloudflare.com/workers-ai/models/stable-diffusion-v1-5-inpainting/index.md); [flux-2-klein-4b](https://developers.cloudflare.com/workers-ai/models/flux-2-klein-4b/)). klein 4B 가중치는 Apache 2.0이라 라이선스도 가장 깨끗하다([HF FLUX.2-klein-4B](https://huggingface.co/black-forest-labs/FLUX.2-klein-4B)).

다른 무료 수단도 Workers AI를 대체하지 못한다. Gemini API는 2026-10-16 기준 모든 이미지·영상 모델에 무료 등급이 없다. 무료 등급 입력은 제품 개선에 쓰인다고 명시돼 있어, Mega Crit 아트를 올리기에도 부적절하다([Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing)). Hugging Face ZeroGPU는 무료 계정에 하루 3.5 GPU분만 준다. 무거운 모델을 한두 번 평가해 보는 용도에 그친다([HF ZeroGPU](https://huggingface.co/docs/hub/spaces-zerogpu)). 로컬 M3·24 GB는 이미지 작업에 실용적이다. klein 4B는 VRAM 13 GB면 돌고([HF](https://huggingface.co/black-forest-labs/FLUX.2-klein-4B)), M1 Max에서 1024 px 한 장에 30~40초가 걸렸다([lilting.ch](https://lilting.ch/en/articles/flux2-klein-4b-mflux-iris-m1-max)). 기본 M3라면 장당 1~2분 이상으로 추정되지만, 밤새 돌리면 사실상 무제한이다. 무료 Mac 앱 Draw Things는 FLUX.2와 Qwen Image Edit 2511을 지원한다([App Store](https://apps.apple.com/us/app/draw-things-offline-ai-art/id6444050820)). 반면 이미지→영상은 실용성이 없다. M1 Max 64 GB에서 Wan 2.2 14B가 **2초 클립 하나에 82분**이 걸렸다([lilting.ch](https://lilting.ch/en/articles/ltx2-wan22-mac-local-video-gen)). 게다가 i2v는 매 프레임 모든 픽셀을 다시 그려서 화풍 흔들림과 이음매가 생긴다.

'바닐라라고 믿을 만한' 품질은 새 픽셀을 덜 만드는 쪽에서 나온다. 상용 선례도 같은 결론이다. Hearthstone 골드 카드는 원본 일러스트에 Photoshop으로 색상별 마스크를 칠하고, 카드당 최대 4개의 셰이더 레이어로 움직인다. 팔처럼 크게 움직이는 부위만 원본에서 지우고(paint-out) 따로 얹는다. **한 사람이 하루 3~4장**을 처리했다([Jon Briggs, 2015](https://hearthstone.blizzard.com/en-us/blog/18053404/)). 반대 극단인 Gwent 프리미엄 카드는 2D 일러스트를 3D 부조로 재구성해 리깅했고, 카드당 약 720인시가 들었다고 보도됐다([Push Square](https://www.pushsquare.com/news/2017/03/pax_east_2017_cd_projekt_red_panel_delves_into_the_premium_cards_featured_in_gwent)). 아래 표는 작업별로 무료 수단이 바닐라 수준에 도달할 가능성을 정리한 것이다([무료 AI 파이프라인 노트](<../research_notes/슬더스2 카드 아트 모드 타당성/free_ai_art_pipeline.md>)).

| 작업 | 바닐라 신뢰도 | 권장 수단 | 쓰는 등급 |
|---|---|---|---|
| 프레임 안 흐름·일렁임 | 높음 | 손으로 칠한 RGBA 마스크와 공용 셰이더. 생성 없음 | 기본·일반 |
| 전경·배경 분리 | 높음 | BiRefNet(MIT)이나 SAM 2로 마스크를 만들고 가장자리는 손질. 원본 픽셀 100% 유지 | 고급 이상 |
| 시차용 깊이 | 높음 | Depth Anything V2 Small(Apache-2.0). Base·Large는 비상업 라이선스라 피한다 | 희귀 일부 |
| 가려진 배경 채움 | 좁은 띠면 중상 | 최대 이동 폭만큼의 띠만 klein 4B로 편집하고 마스크로 합성한 뒤 덧칠 | 희귀 |
| 소형 스프라이트(파편, 연기, 베기) | 중상 | 원본 그림 크롭, 게임 VFX 텍스처, 참조 기반 klein 4B 순으로 시도하고 덧칠 | 희귀·고대의 존재 |
| 아웃페인팅, 프레임 밖 새 인물·환경 | 낮음~중간 | 피한다. 기존 컷아웃이 넘치게 하는 연출로 대체 | – |
| 이미지→영상 루프 | 낮음 | 쓰지 않는다. 엔진 안 시차·메시·셰이더로 대체 | – |

이 설계에서 무료 할당은 병목이 아니다. 거친 추정으로, 희귀 160장에 장당 시행 10~20회를 잡아도 1,600~3,200회다. 이는 Workers AI 무료 할당의 20~40일분이고, 넘치는 양은 로컬 klein 4B로 처리하면 된다. **진짜 병목은 마스크 칠과 덧칠이라는 사람의 노동이다.** Hearthstone 속도인 하루 3~4장을 그대로 적용해도 598장 전체는 150~200인일 규모다(추정). 프레임 밖 상호작용용 추가 아트를 가장 싸고 원작답게 얻는 길은 생성보다 재사용이다. `VfxCmd`가 쓰는 게임 자체의 베기·둔기·번개 VFX 씬, 크리처 Spine 리그, 카드 그림 자체의 크롭이 그 재료다. 다만 게임 VFX 씬을 모드가 직접 띄우는 것은 코드 구조상 가능해 보이지만 실증하지는 않았다([sts2.dll 디컴파일](<../research_notes/슬더스2 카드 아트 모드 타당성/sts2_card_rendering_internals.md>)).

배포 위생도 같은 방향을 가리킨다. 공식 아트를 재인코딩해 싣지 말고, 런타임에 게임 텍스처를 참조하는 마스크·리그·셰이더 파라미터 같은 '델타'만 배포한다. ArtRoller가 "변경된 아트를 이미지로 싣는 대신 런타임에 렌더링한다"며 이 방식을 쓴다([ArtRoller](https://github.com/Shadowfall-Team/ArtRoller)). 고해상도 마스크 정렬에 쓸 원본도 게임 안에 있다. PCK의 `images/packed/card_portraits/`에 PNG 910장(베타 284장 포함)이 들어 있고([sts2.dll 디컴파일](<../research_notes/슬더스2 카드 아트 모드 타당성/sts2_card_rendering_internals.md>)), HighResolutionCards 모드가 이미 이 고해상도 초상화를 불러 쓴다([Nexus #536](https://www.nexusmods.com/slaythespire2/mods/536)). Mega Crit 아트로 스타일 LoRA를 학습시키는 방법은 기술적으로는 가장 강한 화풍 고정이다. 하지만 공동창업자 Casey Yano가 공개 비판한 바로 그 용도이므로 금지한다([PCGamesN](https://www.pcgamesn.com/slay-the-spire-2/art-direction)). Workers AI가 입력을 학습에 쓰는지는 확인하지 못했다. 원본 아트를 올리기 전에 약관을 확인해야 한다.

## (4) 검증의 정본은 Godot 4.5.1 샌드박스, 사이트는 근사 미리보기다

**판정: 사이트 백과사전·카드 타일 조합기를 정본 검증기로 고집하지 않는다. 게임과 같은 버전의 로컬 Godot 샌드박스를 정본으로 삼고, 사이트는 그 웹 빌드를 dev 전용 라우트에 iframe으로 띄우는 창구로 쓴다.** 사용자가 걱정한 두 방향이 모두 사실이기 때문이다. 먼저 Godot VFX를 웹으로 옮기는 일은 너무 어렵다. Godot 4.7 공식 문서는 여전히 "C#으로 작성한 Godot 4 프로젝트는 현재 웹으로 export할 수 없다"고 명시하고, 웹 대상은 WebGL 2.0의 Compatibility 렌더러뿐이다([Godot Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)). 이 사이트도 2026-08-02에 범용 Godot 셰이더→웹 변환기는 없다고 결론 냈다. GPUParticles2D는 Canvas 2D로 근사하고, 일부 셰이더는 8프레임 플립북으로 굽고 있다([CHARACTER_FORM_VFX_STATUS.md](../docs/CHARACTER_FORM_VFX_STATUS.md)). 반대로 사이트만으로는 게임 내 구현을 담기에도 부족하다. 훅 로직은 게임의 C# `N*` 클래스 안에서 돌아서 웹에서 재현할 수 없다.

정본 검증기(Tier 1)는 모드 레포 안의 `tools/card-art-sandbox/`다. Godot 4.5.1 비-.NET 에디터로 만든 GDScript 전용 프로젝트로, 모드가 싣는 바로 그 `.tscn`·`.gdshader`·`.tres`를 같은 `res://` 구조로 읽는다. 이것이 가능하려면 **"아트 씬에는 스크립트를 넣지 않는다"**는 저작 계약이 필요하다. 아트 씬은 `hover`, `drag`, `play` 같은 이름 붙은 AnimationPlayer 애니메이션과 셰이더 uniform 계약만 갖는다. 트리거는 게임에서는 C# 로더가, 샌드박스에서는 GDScript 목업이 건다. 감염 오버레이의 공포증 모드 토글러처럼 게임의 C# 스크립트를 재사용해야 하는 경우에도, 씬에 박지 말고 로더가 런타임에 붙이도록 한다. 카드 프레임 목업은 추출 텍스처와 `card.tscn`의 기하(초상화 250×190, 프레임 300×422)로 재구성한다([sts2.dll 디컴파일](<../research_notes/슬더스2 카드 아트 모드 타당성/sts2_card_rendering_internals.md>)). 데스크톱에서 실행하는 이 샌드박스는 게임과 같은 셰이더 컴파일러, 파티클, AnimationPlayer 구현을 쓰고, 기준 프레임 PNG를 뽑아 회귀 비교에 쓸 수 있다.

"사이트에서 느낌을 본다"는 바람은 이 샌드박스를 단일 스레드로 웹 export해 이어 붙이는 방식으로 채운다. 단일 스레드 export는 기본값이라 COOP/COEP 헤더가 필요 없다. 기본 템플릿이면 수십 MB지만, 기능을 끈 커스텀 템플릿과 Brotli 전송을 쓰면 2.7~4 MB 수준까지 줄어든 실측 사례가 있다([popcar.bearblog.dev](https://popcar.bearblog.dev/how-to-minify-godots-build-size/); [Godot-Web-LoadingTest](https://github.com/JohannesDeml/Godot-Web-LoadingTest)). 사이트에는 `NODE_ENV` 가드와 빌드 제외 장치(예: dev 전용 page 확장자)를 둔 라우트를 만들고, 그 안에서 iframe으로 띄운다. 이렇게 하면 prod Cloudflare 빌드에 섞이지 않고, VFX를 한 줄도 포팅하지 않고도 사이트 맥락에서 연출을 볼 수 있다. 기존 `card-tile.tsx` 위에 WebGL2 레이어를 얹어 공용 셰이더 3~5종을 손으로 포팅하는 Tier 2는 뒤로 미룬다. 셰이더 계약이 안정된 뒤에도 꼭 필요할 때만 한다. 범용 셰이더 변환기, `hint_screen_texture`·`light()`·SDF를 쓰는 셰이더, 파티클의 픽셀 일치는 시도하지 않는다([저작·미리보기 노트](<../research_notes/슬더스2 카드 아트 모드 타당성/animation_authoring_and_preview.md>)).

서드파티 목업 도구 가운데 로컬 에디터보다 나은 것은 없다. 공식 Godot 웹 에디터는 "preliminary" 단계이고 Compatibility 전용이며, C#·GDExtension·export를 지원하지 않는다. 그래서 Spine 미리보기가 불가능하다([Godot 4.4 Using the Web editor](https://docs.godotengine.org/en/4.4/tutorials/editor/using_the_web_editor.html)). ShaderToy나 godotshaders.com은 Godot canvas_item의 블렌드·변환 의미론을 재현하지 않는다. Rive는 무료 플랜 결과물에 스플래시가 붙고 공식 Godot 런타임이 없으므로([Rive pricing](https://rive.app/pricing)), 게임과 같은 결과를 보증할 수 없다. 남는 불확실성은 하나다. 게임이 Forward+·Mobile·Compatibility 중 어느 렌더러를 쓰는지 PCK에서 확인하지 못했다. 게임이 Compatibility가 아니라면 웹 빌드의 블렌드·글로우가 다를 수 있다. 그래서 PoC에서 같은 씬을 게임과 샌드박스에 한 번씩 띄워 비교해야 하고, 최종 승인은 언제나 게임 안에서 한다.

가장 가까운 경쟁자들의 한계가 곧 빈자리다. IroncladFX는 아이언클래드 10장뿐이고, 희귀도 체계와 카드 아트 내부 애니메이션이 없으며, 일부 연출이 무대에 남는다. Animated Rare Cards는 주제상 가장 가깝다. 하지만 Nexus에만 있고, 이름에 "AI generated"를 달았으며, 출시 후 갱신이 없고, DL 608·추천 4로 반응이 미미하다. 같은 시기 정적 AI 애니메 팩은 수만 DL을 기록했으므로, 원인은 주제보다는 품질·노출·플랫폼에 있었을 가능성이 크다. 다만 화면을 확인하지 못해 단정할 수는 없다([Nexus #851](https://www.nexusmods.com/slaythespire2/mods/851)). 규모상 최대 위협은 Regent FX Omnistar와 More X Animations 시리즈다. 카드 아트를 움직이지는 않지만 **사용 순간의 시선과 연출 슬롯을 수십만 사용자 규모로 이미 점유했다.** 같은 카드에서 겹치면 과잉 연출이 된다. 상용 선례가 주는 교훈은 실패 패턴이다. Hearthstone 개발자 회고에는 다음 사례가 나온다. 처음 만든 애니메이션이 최종본보다 약 400% 빨라 산만했다. 같은 효과를 남용해 팀 안에서 "drool-tech"라고 불렸다. 하수인이 뛰어오르는 애니메이션 때문에 초상화 슬롯이 비어 버렸다([Jon Briggs, 2015](https://hearthstone.blizzard.com/en-us/blog/18053404/)).

그래서 이 모드의 독창성은 '새 개념'이 아니라 '체계화된 절제'에 있다. 희귀도로 연출 예산을 배분하는 위계, 일반은 액자 안에 머문다는 규칙, "아무것도 남지 않는다"는 명시적 비지속, 집을 때 시작해 사용할 때 터지는 같은 아트의 연속 연출, 그리고 다른 VFX 모드를 감지하면 틀 밖 연출을 양보하는 공존 설계가 그 내용이다. 마지막 항목은 기능이면서 차별점이다. 홍보할 때는 "Marvel Snap식 등급 연출을 STS2 공식 아트에, 바닐라처럼"이라는 프레이밍이 정확하다.

## 레포 구성안과 PoC부터의 4단계 로드맵

권장 레포는 SLS2Mods와 ModTemplate 구조를 따르는 멀티모드 모노레포다([SLS2Mods](https://github.com/luojiesi/SLS2Mods); [ModTemplate-StS2](https://github.com/Alchyr/ModTemplate-StS2)). 이름과 모드 id는 예시다.

```text
slseoun-mods/
├─ Directory.Build.props        # GodotPath(MegaDot 4.5.1), Sts2Path, sts2.dll·0Harmony.dll 참조(Private=false)
├─ mods/
│  ├─ SlseounLivingArt/         # 핵심 모드: 생성 픽셀 0 (셰이더·컷아웃·게임 VFX 재사용)
│  │  ├─ SlseounLivingArt.csproj   # Godot.NET.Sdk/4.5.1, net9.0
```

사이트 쪽 변경은 하나다. dev 전용 라우트를 만들고, 환경 변수로 지정한 모드 레포 경로에서 `manifest/cards.json`과 샌드박스 웹 빌드를 읽어, 기존 카드 타일·Spine 무대 옆에 iframe으로 띄운다. 이 라우트는 prod 빌드에서 아예 컴파일되지 않게 한다. 공식 아트 PNG는 모드 레포가 공개 레포라면 커밋하지 않는다.

| 단계 | 범위 | 핵심 산출물 | 종료 조건 |
|---|---|---|---|
| 0. 기반 | 레포·빌드 체인 | 빈 모드(`affects_gameplay:false`), 카드 한 장의 `%Portrait` 아래 클립 사각형 | 게임에서 로드된다. 바닐라 피어와 협동 접속이 된다. 패치 대상이 없을 때 해당 기능만 꺼진다 |
| 1. PoC | 일반·고급·희귀 각 1장 (한 캐릭터, 희귀는 무색도 가능) | 마스크 셰이더, 컷아웃 스필, 손패 팝아웃과 무대 덧그리기, Tier 1 샌드박스, klein 4B 좁은 띠 채움 A/B | 아래 다섯 질문에 답한다 |
| 2. 체계화 | 공용 셰이더, 매니페스트, 설정, 공존 | 초상화 해시 게이트, FastMode·PhobiaMode·흔들림 매핑, 다른 VFX 모드 감지·양보, (선택) 사이트 dev 라우트 | PoC 3장이 게임 패치 1회를 무사히 넘긴다 |
| 3. 첫 공개 | 한 캐릭터의 기본·일반·고급 약 62~64장 (AI 0) + 희귀 쇼케이스 3~5장 | Workshop·Nexus 동시 배포, 한·중·영 설명, 공정 공시 | 성능·호환 피드백을 한 바퀴 반영한다 |
| 4. 확장 | 캐릭터별 희귀 27장씩, 무색 희귀 25장, 고대의 존재 19장, (선택) AI 보조 확장 모드 | 캐릭터 단위 릴리스 | 패치마다 스모크 테스트를 통과한다 |

첫 PoC는 의도적으로 작게 잡는다. 대상은 일반·고급·희귀 각 1장이고, 일반·고급은 한 캐릭터에서 고른다. 카드는 세 기준으로 고른다. 경쟁 모드와 바닐라 고유 VFX가 점유하지 않은 카드여야 한다. 일반 카드는 불·연기·물처럼 '흐르는' 재질이 그림에 있어야 셰이더가 빛난다. 희귀 카드는 전경 실루엣이 뚜렷해야 컷아웃이 깨끗하다. 피해야 할 카드는 다음과 같다. IroncladFX와 More Ironclad Animations가 손댄 악마의 형상, 바리케이드, 지옥불, 불타는 조약, 분노, 낙인, 몸통 박치기 등. Regent FX Omnistar가 손댄 빛나는 타격, 태양의 타격, 혜성, 초질량, 방출. Better Animation이 손댄 메아리의 형상, 암살, 얼음 창. 그리고 바닐라가 전용 사용 연출을 가진 발화, 지옥검무, 칼날 부채, 불의 심장이다([유사 모드 노트](<../research_notes/슬더스2 카드 아트 모드 타당성/similar_mods_originality.md>); [sts2.dll 디컴파일](<../research_notes/슬더스2 카드 아트 모드 타당성/sts2_card_rendering_internals.md>)). 희귀 1장은 무색 희귀 25장에서 고르는 것도 방법이다. 캐릭터별로 묶인 경쟁 VFX 모드와 겹칠 가능성이 낮다(추정). PoC가 답할 질문은 다섯 가지다. (a) 손패 10장에서 hover·집기 중일 때 프레임 비용은 얼마인가. (b) 같은 씬이 샌드박스와 게임에서 다르게 보이는가(렌더러 문제). (c) 블라인드 비교에서 일반·고급 연출이 바닐라로 읽히는가. (d) klein 4B 좁은 띠 채움이 100% 확대에서 티 나는가(Workers AI와 로컬 비교). (e) 사용 연출이 0.25·0.1·0.01초 이동 창 안에서 읽히면서도 추가 타격으로 오인되지 않는가. 첫 공개를 AI 0인 등급으로 채우는 순서는 의도된 것이다. 물량이 가장 많은 등급을 평판 위험 없이 먼저 내고, AI 보조가 필요한 희귀 확장은 반응을 본 뒤 별도 모드로 공시해 낸다.

## 네 가지 위험: AI 반감, EA 파손, VFX 모드 충돌, modded 세이브

| 위험 | 근거 | 완화 |
|---|---|---|
| 커뮤니티 AI 반감과 Mega Crit 입장 | Yano의 반AI 공개 입장, Steam 토론 답글 62개, Nexus의 AI 태그 의무화 | 출하 픽셀 AI 0을 핵심 모드 기본값으로, AI 보조분은 별도 모드로 분리·공시, LoRA 금지, 델타만 배포 |
| EA 패치 파손 | private 메서드·씬 경로 변경, v0.110.0 초상화 교체, `max_game_version` 필드 없음 | 훅 누락 시 기능 끄기, 카드별 초상화 해시가 다르면 정지 초상화로 후퇴, 패치마다 스모크 테스트 |
| 경쟁 VFX 모드와의 중복·호환 | 같은 카드, 같은 사용 시점, 수십만 구독 | 로드된 모드 목록을 감지해 해당 카드의 틀 밖 연출만 양보, 카드별 끄기 |
| modded 세이브 분리 | 모드가 하나라도 로드되면 `modded/` 프로필 사용 | 설치 안내에 명시, 제거 시 동작 설명 |
| 협동 접속 차단 | `affects_gameplay` 기본값 true | 매니페스트에 false 명시, 모델·넷 메시지 정의 금지 |
| 게임플레이 신호 혼동·성능 | Hearthstone 회고, GIF 모드 성능 비판 | 노출 시간에 반비례하는 소음 규칙, 활성 카드만 재생 |

**AI 반감은 이 기획에서 특히 날카롭다.** 생성형 AI에 대한 커뮤니티 반응 자체는 갈린다. 원작을 애니메 화풍으로 대체한 AI 팩은 크게 받아들여졌다. Regent Cards Anime Rework는 Nexus DL 93,597·Workshop 구독 75,797이고([Nexus #344](https://www.nexusmods.com/slaythespire2/mods/344)), AI 생성 콘텐츠를 공시한 Merchant2CuteII도 구독 234,389다([Steam Workshop](https://steamcommunity.com/sharedfiles/filedetails/?id=3748331824)). "NO AI" 표기 팩은 DL 642와 250에 머문다([Nexus #1157](https://www.nexusmods.com/slaythespire2/mods/1157); [Nexus #469](https://www.nexusmods.com/slaythespire2/mods/469)). 하지만 이 기획은 '원작을 대체'하지 않고 **'원작과 구별되지 않게' AI를 쓰는** 쪽이다. 이것은 Casey Yano가 비판한 용도와 정확히 겹친다. 그는 AI가 자기 아티스트의 화풍을 흉내 내는 것을 보면 아티스트가 슬퍼할 것이고, 고유한 화풍이 이미 있으니 AI로 복제할 이유가 없다고 말했다([PCGamesN](https://www.pcgamesn.com/slay-the-spire-2/art-direction); [GameSpot](https://www.gamespot.com/articles/slay-the-spire-2-is-choosing-shit-art-over-generative-ai/)). Mega Crit Content Policy는 표절이나 차별적 모욕이 아닌 모드를 허용하고, 공식 제휴를 암시하거나 유료화하는 것만 금지한다. 생성형 AI 금지 조항은 굿즈와 갤러리 제출물에만 걸려 있다. 다만 이는 요약 조회 기준이므로 공개 전에 원문을 다시 확인해야 한다([Mega Crit Content Policy](https://www.megacrit.com/content-policy)). STS2 Steam 토론 "Ai used in mods on the workshop"(답글 62개)은 "작가에게서 훔친다"는 반대와 "slop만 아니면 된다"는 수용으로 갈렸다([Steam 토론](https://steamcommunity.com/app/2868840/discussions/0/571542424813443618/)). Nexus는 AI 사용을 세 종류 태그로 공시하게 하고, 공시하지 않으면 중재 대상으로 삼는다([Nexus 공지](https://www.nexusmods.com/dispatch/news/14850)). 그래서 레포 구조 자체를 완화책으로 쓴다. 핵심 모드는 출하 픽셀에 AI가 0이다. 분할 마스크 보조처럼 공정에 AI를 쓴 부분은 정확히 공시한다. 생성 채움이 들어간 희귀 확장은 별도 모드로 내고 Nexus 태그를 단다.

**EA 패치 파손은 코드와 아트 양쪽에서 온다.** 코드 쪽에서는 2026-03-18 핫픽스 뒤 모드 폴더가 인식되지 않고 여러 모드가 작성자 업데이트를 기다려야 했다는 보고가 있었다([Steam 토론](https://steamcommunity.com/app/2868840/discussions/0/798964766335869993/)). "베타 패치가 특히 BaseLib를 자주 깨뜨린다"는 안내도 있고([sts2.gg](https://sts2.gg/mods/install-guide)), BaseLib는 7월 말부터 9월 중순 사이에 다섯 번 릴리스됐다([BaseLib-StS2](https://github.com/Alchyr/BaseLib-StS2)). 매니페스트에는 `min_game_version`만 있고 상한 필드는 없어서, 새 버전에서 깨지는 것을 로더가 막아 주지 않는다([생태계 노트](<../research_notes/슬더스2 카드 아트 모드 타당성/sts2_modding_ecosystem.md>)). 아트 쪽 파손은 더 조용하다. v0.110.0은 여러 카드의 초상화를 다듬어 교체했다([v0.110.0 패치노트](../data/sts2-patch-notes/v0.110.0.md)). 이런 교체가 일어나면 카드별 마스크가 엇나간 채 계속 재생된다. 매니페스트에 원본 초상화의 크기·해시를 적어 두고, 런타임 텍스처와 다르면 그 카드만 정지 초상화로 돌아가게 한다. 이 장치는 베타 아트 284장을 띄우는 Beta Art Enabler 사용자에게도 같은 이유로 필요하다([Nexus #683](https://www.nexusmods.com/slaythespire2/mods/683)).

**경쟁 VFX 모드와의 충돌은 같은 순간을 두고 벌어진다.** Harmony postfix는 여러 모드가 같은 메서드에 걸어도 공존하므로, 문제는 크래시보다 시각적 과잉이다. 바닐라 자체도 발화, 지옥검무, 칼날 부채, 불의 심장에서 `OnEnqueuePlayVfx`를 오버라이드해 전용 연출을 띄운다([sts2.dll 디컴파일](<../research_notes/슬더스2 카드 아트 모드 타당성/sts2_card_rendering_internals.md>)). 로드된 모드 목록을 보고 같은 캐릭터를 다루는 VFX 모드가 있으면, 해당 카드의 틀 밖 연출을 끄고 프레임 안 연출만 남긴다. 사용자가 카드별로 끌 수도 있게 한다.

**"모드를 지우면 아무것도 안 바뀐다"에는 단서가 붙는다.** 게임플레이는 바뀌지 않는다. 그러나 `IsRunningModded()`는 `affects_gameplay`와 무관하게 모드가 하나라도 Loaded 또는 Failed 상태면 true다. 그 결과 프로필·진행도·런 세이브가 `modded/` 폴더로 분리된다. 첫 모드 실행 때 기존 세이브가 복사되고, 지표 업로드와 Sentry가 꺼지며, 개발 콘솔 디버그 명령이 열린다([sts2.dll 디컴파일](<../research_notes/슬더스2 카드 아트 모드 타당성/sts2_card_rendering_internals.md>)). v0.110.0부터는 세션에 모드 사용자가 있으면 오류 대화상자의 "Report Bug" 버튼도 숨겨진다([v0.110.0 패치노트](../data/sts2-patch-notes/v0.110.0.md)). 모드가 켜진 동안의 진행은 `modded/` 쪽에 쌓이고, 모드를 지우면 원래 세이브로 돌아간다. 그래서 설치 안내에 "이 모드를 쓰는 동안의 진행도는 모드 전용 프로필에 저장된다"를 첫 줄로 넣어야 한다. 모드 사용 시 Steam 업적과 일일 도전 리더보드가 제한되는지, macOS에서 앱 번들 안의 `mods/` 폴더가 Steam 업데이트·코드 서명과 어떻게 상호작용하는지는 확인하지 못했다.

## 결론

이 조사에서 가장 쓸모 있는 발견은 서로 다른 세 문제가 같은 처방으로 수렴한다는 점이다. 그 처방은 **생성 픽셀을 최소화하라**는 것이다. 첫째는 품질이다. 바닐라라고 믿을 만한 결과는 원본 픽셀을 남기는 마스크·컷아웃·셰이더 공정에서 나온다. 둘째는 IP다. 게임 텍스처를 런타임에 참조하고 델타만 배포하면 공식 아트를 재배포하지 않는다. 셋째는 평판이다. 핵심 모드의 출하 픽셀을 AI 0으로 두면 Mega Crit의 반AI 입장과 정면충돌하지 않는다. 레포 분리는 이 처방을 패키징으로 구현하는 하부 구조다. AI 보조 콘텐츠를 별도 모드로 떼어 공시할 수 있는 것은 멀티모드 레포이기 때문이다. Workers AI를 우선하라는 출발점은 그대로 두되, 그 역할은 '아트를 만드는 엔진'에서 '좁은 틈을 메우는 도구'로 바뀐다.

두 번째 발견은 이 모드의 진짜 자산이 그림보다 **계약**이라는 점이다. `affects_gameplay:false`, UI 계층 postfix만 쓰기, 훅 누락 시 기능 끄기, 초상화 해시가 다르면 후퇴하기, 경쟁 모드에 양보하기라는 규칙이 그 계약이다. 이 규칙들은 데코레이터 원칙의 구현이면서 동시에 EA 파손, 협동 호환, 경쟁 모드 공존에 대한 방어선이다. 비용의 병목은 무료 연산이 아니라 사람의 마스크 칠과 덧칠이다. 희귀도 사다리는 연출 위계이면서 노동을 배분하는 예산표이기도 하다. 첫 PoC가 증명해야 할 것은 "움직이게 할 수 있는가"가 아니다. **"블라인드 비교에서 바닐라로 보이는가"**다.
